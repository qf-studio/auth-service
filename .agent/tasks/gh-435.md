## Context

**Problem** (from #435, found standing up Pointer's stack): the image ships only the server binary, and the service FATALs on missing tables. Consumers must vendor the SQL migrations out of the repo (Pointer vendored them under `test/fixtures/auth-migrations/`; its deploy workflow checks out this repo just to mount `migrations/` into a `migrate/migrate` container). Item 2 of the issue (from-scratch UUID/TEXT FK breakage) was already fixed in #445/v0.68.1 — **this task is only item 1: ship migrations in the image**.

**Codebase facts** (verified 2026-07-26):
- Migrations are embedded at compile time: `migrations/embed.go` (`//go:embed *.sql` → `migrations.FS`), consumed by `cmd/migrate/main.go` via iofs source. The migrate binary is therefore **fully self-contained** — no SQL files need copying into the image.
- `cmd/migrate/main.go` reads `DATABASE_URL` or `POSTGRES_HOST/DB/USER/PASSWORD` env; supports `up|down|version` (`main.go:18,93-121`) but **not `force`** — add `force <N>` (calls `m.Force(N)`), needed for dirty-state recovery (see the 2026-07-24 Pointer incident: failed migration left `schema_migrations` dirty and consumers had no in-image recovery path).
- `docker/Dockerfile`: two-stage (golang:1.25-alpine → alpine:3.21), builds only `./cmd/server`, runs as `appuser`, `ENTRYPOINT ["/auth-service"]`.
- ⚠️ **Latent multi-arch bug to fix in the same file**: `.github/workflows/release.yml:55` builds `linux/amd64,linux/arm64`, but the Dockerfile hardcodes `GOARCH=amd64` — the arm64 image currently ships an amd64 binary. Use buildx's `TARGETOS`/`TARGETARCH` build args for **both** binaries.

## Implementation Plan

### Phase 1: Dockerfile
- [ ] Builder stage: declare `ARG TARGETOS TARGETARCH`; build with `GOOS=${TARGETOS:-linux} GOARCH=${TARGETARCH:-amd64}`.
- [ ] Build `./cmd/migrate` → copy into runtime stage as `/auth-migrate` (same `-trimpath -ldflags="-s -w"` flags).
- [ ] Keep `ENTRYPOINT ["/auth-service"]` unchanged — migrations run via `docker run --entrypoint /auth-migrate <image> up`.

### Phase 2: Verify wiring in CI
- [ ] Extend the Release workflow's `migration-dry-run` job (`.github/workflows/release.yml`): after the image build, run migrations against the job's Postgres service **using the built image's `/auth-migrate`** instead of (or in addition to) `go run cmd/migrate/main.go`. This proves the shipped tool works on every release. (Job ordering: it already `needs: release`; pull the just-pushed sha-tagged image.)

### Phase 3: Docs
- [ ] `deployments/README.md`: "Running migrations from the image" section with the `--entrypoint /auth-migrate` invocation and required env (`DATABASE_URL` / `POSTGRES_*`).
- [ ] Comment on #435 with the consumer migration path so Pointer can drop its vendored fixtures and the checkout step in `deploy-pointer-aws.yml` (do NOT modify `deploy-pointer-aws.yml` in this task — it is actively used by the Pointer team; leave switching it to the image tool as their follow-up).

## Technical Decisions

| Decision | Options | Chosen | Reasoning |
|---|---|---|---|
| Delivery | copy SQL dir into image + migrate/migrate; separate migrate image; second binary in same image | Second binary `/auth-migrate` | Migrations already embedded — zero extra files; one image to pin; matches "migrations run from the same release as the server binary" contract |
| Invocation | subcommand of server binary vs separate binary | Separate binary | `cmd/migrate` already exists; no server-flag surgery; `--entrypoint` override is standard practice |
| Multi-arch | leave GOARCH=amd64 | `TARGETOS`/`TARGETARCH` args | arm64 images currently ship amd64 binaries; fix while touching the file |
