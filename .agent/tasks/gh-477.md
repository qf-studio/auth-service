# GH-477

**Created:** 2026-07-29

## Problem

GitHub Issue GH-477: feat(email): wire EmailSender and deliver password-reset links (TODO at internal/auth/service.go:323)

## Context

auth-service sends zero email today. `internal/email` has the full scaffolding — `EmailSender` interface (`email.go:19`), dev `ConsoleSender` (`console.go`), production `HTTPSender` (`http.go:14-83`, POSTs `{serviceURL}/send-email` with Bearer auth) — all unit-tested and **never constructed**: the package has no importers, `cmd/server/main.go` doesn't reference it, and `auth.Service` takes no email dependency. `EmailConfig` (`internal/config/config.go:89-94`, env `EMAIL_SERVICE_URL`/`EMAIL_API_KEY`/`EMAIL_SENDER_ADDRESS`/`EMAIL_ENABLED` default false, loaded at `config.go:553-569`) is parsed and unused.

`ResetPassword` (`internal/auth/service.go:300-326`) is complete minus delivery: generates a 32-byte token, stores `pw_reset:<token>→email` in Redis (30 min TTL), audits — then stops at the TODO at `service.go:323`. `ConfirmPasswordReset` already validates/consumes the token and revokes sessions. Routes are wired (`internal/api/router.go:97-98`) and the handler always returns 202 (anti-enumeration).

The delivery target is pilot-console's new `POST /send-email` (qf-studio/pilot-console#61), which implements exactly the contract `HTTPSender` already speaks — no client changes needed here.

## Task

- `cmd/server/main.go`: construct the sender from `EmailConfig` — `EMAIL_ENABLED=false` → `ConsoleSender`, `true` → `HTTPSender`; add the cross-field validation `loadEmail` lacks (enabled ⇒ ServiceURL/APIKey/SenderAddress all set, fail startup otherwise).
- `auth.NewService`: accept an `EmailSender` (keep the parameter list tidy — options struct if the constructor is already wide).
- At `service.go:323`: **look up the user by email first**. Unknown email → keep the 202, skip token storage AND send (today a token is stored for any address — tighten this). Known user → send the reset link `${PASSWORD_RESET_URL_BASE}?token=<token>` — new env `PASSWORD_RESET_URL_BASE`, validated when `EMAIL_ENABLED=true`.
- Send failures: log + audit, still 202 (delivery failure must not become an enumeration oracle).

## Acceptance criteria

- Unit tests with a fake sender: existing user → exactly one `Send` whose body contains the link with the token; unknown email → zero sends, zero Redis writes, still 202; `EMAIL_ENABLED=false` → ConsoleSender path exercised.
- Config cross-validation: enabled-with-missing-fields fails startup with a clear error.
- Existing reset/confirm tests stay green.

## Non-goals

Signup verification (separate issue, depends on this one), HTML templates, MFA email, resend/rate-limiting of reset requests.
