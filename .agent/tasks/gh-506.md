# GH-506

**Created:** 2026-09-06

## Problem

GitHub Issue GH-506: feat(tokens): per-application aud for access tokens (replace the single global JWT_AUDIENCE)

## Problem

auth.quantflow.studio is the studio's central auth (v0.72.0 on AWS since 2026-09-06). One global `JWT_AUDIENCE` (`internal/config/config.go` lines 155, 440-441, 453 → `[]string`) is stamped on every access token at `internal/token/service.go` lines 411-412, regardless of the requesting client. Products will be integrated one by one (Pointer first, then the studio website, the Pilot console), so a token minted for one product must not validate at another.

Second gap found during research: `aud` is never enforced. `ValidateToken` (`internal/token/service.go` ~line 484) parses without `jwt.WithAudience`; `internal/domain/claims.go` lines 52-56 document this as deliberate ("not validated … to avoid breaking tokens issued before an audience was configured"); `internal/token/service_test.go` lines 415-421 assert the permissive behaviour. Per-app audiences without validation would be decoration.

## Design

- Client model: add `Audience []string` to `internal/domain/client.go` `Client` (nullable/empty = inherit global), following the existing per-client override precedent `AccessTokenTTL`. Migration + admin API (`internal/admin` client service) + persistence.
- Issuance: at `service.go:411`, use `client.Audience` when set, else `cfg.Audience`.
- Validation: add audience enforcement in `ValidateToken`, gated by a new config `JWT_AUDIENCE_ENFORCE` (bool, default `false`) so existing consumers (Pointer) keep working until they confirm their expected audience. When enforced: token `aud` must contain the validator's expected audience. Document the flip as the last step of each product's integration.
- Optional, only if cheap: accept RFC 8707 `resource` on the token request and require it to be a subset of the client's allowed audiences. Not required for this issue.
- ID-token `aud` (already `client_id`, see `e2e/oidc_flow_test.go` line 189) unchanged.

## Acceptance

- Two clients with different `Audience` receive access tokens whose `aud` differ; a client with none receives `JWT_AUDIENCE`.
- With `JWT_AUDIENCE_ENFORCE=true`, `ValidateToken` rejects a token whose `aud` lacks the expected value and accepts one that has it; with the flag off, behaviour is byte-identical to today (existing tests unchanged).
- Admin API can set/clear a client's audience; migration is reversible.
- README + env examples document `Audience` and `JWT_AUDIENCE_ENFORCE`.
