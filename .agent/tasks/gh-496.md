## Problem

PR-time E2E can't catch a broken *published* artifact: a bad release-train output, a corrupt GHCR image, or SDK/image drift only surfaces when a consumer pulls the release. Pilot solves the analogous problem with a scheduled synthetic canary against a disposable sandbox repo. Strategy: `.agent/tasks/TASK-01-e2e-canary-strategy.md` (issue D, layer L2).

## Context

- Repo `qf-studio/auth-service-canary` (created 2026-08-31, private, empty stub).
- Pattern source (pilot repo, port faithfully): reusable scenario workflow + idempotency guard (`pilot-canary.yml` / `pilot-canary-scenario.yml`), and `scripts/canary-report.py` — single mutating tracker issue per scenario with JSON state blob and green-streak auto-close (3 green scheduled runs), reopen on failure. Zero service-side code — pilot TASK-379/403 hard constraint carries over.
- Consumes only published artifacts: `ghcr.io/qf-studio/auth-service:<latest release>` + `ghcr.io/qf-studio/auth-service-smoke:<same tag>` (issue C).

## Task

All content lives in the canary repo:

1. **Canary workflow**: triggers = `workflow_dispatch` + `schedule` daily + `repository_dispatch`/`workflow_call` fired from auth-service's release workflow on each release (on-release + daily, per TASK-01 open decision 1). Steps: resolve latest `v*` release tag via `gh api` → compose up postgres/redis + the service image at that tag → run `/auth-migrate up` → run the smoke image at the same tag against it → tear down.
2. **Reporter**: port pilot's `canary-report.py` → tracker issue `[canary:auth-flows]` on `qf-studio/auth-service` (not the canary repo — where humans look). Green-streak auto-close, reopen + state-blob update on failure. Needs a `CANARY_GH_TOKEN` secret with issues:write on auth-service — **Aleks provisions**.
3. **Idempotency/overlap guard**: skip if a previous canary run is still in progress (concurrency group).
4. **Release hook**: one-line addition to auth-service's release workflow to fire the canary after a successful release (must not block or fail the release itself).
5. **README** in the canary repo: what it is, how to read the tracker issue, "safe to nuke" framing, L3 note (same workflow re-pointed at staging via `SMOKE_BASE_URL` override once GH-416 staging exists).

## Acceptance criteria

- `workflow_dispatch` run against the current latest release goes green end to end and closes/updates the tracker issue.
- Killing the service container mid-run produces a failed run and a tracker-issue reopen with the state blob updated (verified once, manually).
- A release in auth-service triggers a canary run automatically.
- Scheduled + release triggers never overlap (concurrency group verified).

## Non-goals

Staging (L3); metrics-isolation flags (ephemeral env — nothing persists); alerting beyond the tracker issue (no Slack for now); load/perf testing.
