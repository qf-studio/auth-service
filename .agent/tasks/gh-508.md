# GH-508

**Created:** 2026-09-06

## Problem

GitHub Issue GH-508: fix(dpop): DPoP htu scheme reconstructed as http behind the ALB — trust X-Forwarded-Proto from configured proxies (SSL 'not working' at auth.quantflow.studio)

## Problem ("SSL is not working" at auth.quantflow.studio)

auth.quantflow.studio runs behind an AWS ALB that terminates TLS; the container receives plaintext HTTP. Two places reconstruct the request URL for DPoP proof validation from Go's per-connection TLS state:

- `internal/middleware/dpop.go` lines 85-92 (`dpopRequestURI`): `if c.Request.TLS == nil { scheme = "http" }`
- `internal/api/token_handlers.go` lines 86-93 (`requestURI`): same pattern

Behind the ALB `c.Request.TLS` is always nil, so the server always builds `http://auth.quantflow.studio/...`. `internal/dpop/dpop.go` `matchHTU` (lines 429-448, scheme equality at 441) then compares that against the client's proof `htu`, which any correct client signs as `https://auth.quantflow.studio/...`. Scheme mismatch → every DPoP-bound request is rejected as an invalid proof. There is no `X-Forwarded-Proto` handling anywhere in the codebase. Edge TLS itself is fine (valid cert, https discovery + JWKS 200, HTTP→HTTPS redirect) — the break is server-side scheme reconstruction.

Verify on the live service: token endpoint with a DPoP proof for `https://auth.quantflow.studio/oauth/token` fails; logs show the htu mismatch.

## Fix

1. Add one helper (e.g. in `internal/middleware`) that derives the public scheme and host for a request: prefer `X-Forwarded-Proto` / `X-Forwarded-Host` when the request came from a trusted proxy, else fall back to `Request.TLS` / `Request.Host`. Trust must be explicit: a config value `TRUSTED_PROXY_CIDRS` (comma-separated CIDRs; default empty = trust nothing, current behaviour). Behind the ALB Nelya sets it to the VPC CIDR(s).
2. Replace both `c.Request.TLS == nil` sites with the helper. `matchHTU` unchanged.
3. Document the new variable in `README.md`, `deployments/README.md`, and the `.env` examples, with the ALB note.
4. Do not touch `TLS_ENABLED` here (#507 removes it).

## Acceptance

- Unit tests in `internal/middleware/dpop_test.go` and `internal/api/dpop_integration_test.go`: request from a trusted proxy IP with `X-Forwarded-Proto: https` validates a proof whose htu is https; same headers from an untrusted IP are ignored (proof with https htu rejected, http htu accepted); no header → unchanged behaviour.
- Spoofing test: `X-Forwarded-Proto` from an untrusted source cannot flip the scheme.
- After deploy with `TRUSTED_PROXY_CIDRS` set, a DPoP token request against auth.quantflow.studio succeeds.
