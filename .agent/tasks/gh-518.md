# GH-518

**Created:** 2026-09-28

## Problem

GitHub Issue GH-518: feat(email): change the account email with confirmation from the new address and revert from the old (TASK-501 leg B, auth-service part)

## Context

TASK-501 leg B. Console users can now edit their display name (PUT /auth/me, #516/#517) and the email transport is live end to end (verification and password-reset mail go auth-service → console relay → SES, smoke passed 2026-09-28). What is still missing is a way to change the account email. It must be confirmed from the new address and revertable from the old one, because an email change is an account-takeover lever.

Ground truth on main (verified 2026-09-28):
- Password re-auth precedent: Service.ChangePassword in `internal/auth/service.go` (line 614) verifies the old password with s.hasher.Verify (line 623) and returns api.ErrUnauthorized when it does not match.
- Session revocation precedent: ConfirmPasswordReset calls RevokeAllForUser on the refresh-token repository (line 549); LogoutAll does the same (line 721).
- Token precedent: generateResetToken (lines 740 to 746) makes 32 random bytes hex; verify tokens live on the users row (email_verify_token, email_verify_token_expires_at, migration 000005), reset tokens live in Redis with GetDel single-use. Links are built as base + "?token=" + token (lines 211 and 466) from deps.VerifyURLBase and deps.ResetURLBase.
- Mail: the EmailSender interface in `internal/email/email.go` has one method Send(ctx, Message{To, Subject, Body}); subjects and bodies are inline strings at the call sites (lines 212 to 216 and 467 to 471).
- Config: EmailConfig in `internal/config/config.go` (lines 111 to 118); loadEmail (lines 606 to 638) requires all five email settings when EMAIL_ENABLED is true.
- Audit constants in `internal/audit/audit.go` (lines 14 to 78), convention EventNounPastTense, e.g. EventProfileUpdated added by #517.
- users table: columns from migrations 000003, 000005, 000010, 000015; unique index users_tenant_email_unique (tenant_id, email); latest migration is `migrations/000020_add_client_audience.up.sql`.
- Rate limiting: only the engine-global mw.RateLimit is wired (`internal/api/router.go` lines 34 to 35). middleware.AccountRateLimiter in `internal/middleware/ratelimit.go` (lines 147 to 276) exists but is not used by any route.

Decisions taken (founder, 2026-09-28): re-auth is the current password (same bar as password change; MFA step-up is not in scope). A confirmed change revokes every refresh token so the user logs in again with the new address.

## Change

State on the users row (new migration 000021, up and down, same style as `migrations/000020_add_client_audience.up.sql`): pending_email text null, email_change_token text null, email_change_token_expires_at timestamptz null, email_revert_token text null, email_revert_token_expires_at timestamptz null, previous_email text null. Unique partial indexes on email_change_token and on email_revert_token where not null. Tokens stay plaintext like email_verify_token (hashing every token column is a separate hardening issue, out of scope here).

Routes (register in `internal/api/router.go`, request structs in `internal/domain/validation.go` with a case each in the ValidateReq switch at lines 180 to 199, handlers in `internal/api/auth_handlers.go`, service methods in `internal/auth/service.go`, repository methods in `internal/storage/user_repository.go` plus `internal/storage/mocks/user_repository.go`):

1. POST /auth/me/email on the protected group, body {"new_email", "password"}.
   - Verify the password exactly as ChangePassword does. On mismatch respond 403 with the existing error shape and code invalid_password. Not 401: the caller is authenticated, and the console and the SPA treat 401 as an expired session and log the user out.
   - 409 when new_email equals the current email (case-insensitive) or another user in the tenant already has it (check users_tenant_email_unique the same way Register does).
   - 422 on an invalid address (reuse the email validation Register uses).
   - Rate limit 3 requests per user per hour with a Redis counter keyed by tenant and user id (same Redis client the reset tokens use); the fourth answers 429 with the existing error shape. Do not wire AccountRateLimiter for this.
   - On success: generate two tokens with generateResetToken; store pending_email, email_change_token with expiry now+24h, email_revert_token with expiry now+7d; a second request while one is pending replaces the pending address and both tokens. Send two mails through the EmailSender: to the NEW address, subject "Confirm your new email", body with confirm link = EmailChangeConfirmURLBase + "?token=" + change token; to the OLD (current) address, subject "Your email is being changed", body naming the new address's domain only and the revert link = EmailChangeRevertURLBase + "?token=" + revert token. A send failure is audited (new event EventEmailChangeEmailFailed, same handling as EventEmailVerifyEmailFailed) and the request still answers 202. Audit EventEmailChangeRequested with the user id.
   - Respond 202 {"status":"pending","pending_email":"<new>"}.
2. POST /auth/email-change/confirm on the public auth group, body {"token"}.
   - Unknown token 400, expired 410 (the console relays pass both through verbatim). Otherwise in one transaction: previous_email = email; email = pending_email; email_verified = true; pending_email, email_change_token and its expiry cleared; revert token kept. If another user took the address in the meantime respond 409 and leave the row unchanged.
   - Revoke all refresh tokens for the user (RevokeAllForUser). Audit EventEmailChanged. Respond 200 {"status":"changed"}.
3. POST /auth/email-change/revert on the public auth group, body {"token"}.
   - Unknown 400, expired 410. If previous_email is set (the change was confirmed): email = previous_email, then clear previous_email, pending_email, both tokens and expiries; 409 if previous_email is now taken by another user. If previous_email is null (the change was only requested): clear pending_email and both tokens, nothing else changes. In both cases revoke all refresh tokens and audit EventEmailChangeReverted. Respond 200 {"status":"reverted"}.

Config: add EmailChangeConfirmURLBase and EmailChangeRevertURLBase to EmailConfig (env EMAIL_CHANGE_CONFIRM_URL_BASE and EMAIL_CHANGE_REVERT_URL_BASE) as optional even when EMAIL_ENABLED is true, so the running deployment keeps booting with its current template. When EMAIL_ENABLED is true and either is empty, log one warning at startup and answer POST /auth/me/email with 503 code email_change_unconfigured. Confirm and revert do not depend on them.

OpenAPI: add the three operations to `api/public.openapi.yaml` next to /auth/me/password; spectral stays clean.
